## Why Render, not Fly.io

Phase 8 originally targeted Fly.io, but Fly removed its card-free free
tier -- `flyctl apps create` now hard-fails with "We need your payment
information to continue" even on the smallest VM. Render's free
web-service tier is genuinely cardless. Tradeoffs accepted:

- **No persistent disk on the free plan.** The SQLite TTL cache
  (`backend/.cache/cache.sqlite`) is ephemeral and rebuilds itself on the
  next request after any restart/redeploy -- this was already the
  intended behavior (it's a cache, not a database), so it costs nothing.
  `backend/data/nifty50.json` (the constituent list) is also on that same
  ephemeral disk -- see the admin-refresh caveat below.
- **Free-plan spin-down.** An idle free instance spins down and the next
  request pays a ~50s cold-start. The scheduled refresh (Step 4) also
  incidentally keeps it warm once a day.

## The Yahoo-from-cloud-IP finding (Step 1 de-risk test)

Tested live against the deployed Render (Singapore region) backend:
5 distinct symbols' `/api/quote/{symbol}` (TCS, RELIANCE, HDFCBANK, INFY,
ICICIBANK -- distinct symbols force a fresh upstream fetch each time,
unlike repeating one symbol which just serves cache) plus one
`/api/financials/TCS` call, all within about two minutes.

**Result: no blocking, no rate-limiting.** All 6 requests returned real,
non-null data (correct live prices, market caps, full income/balance/
cash-flow statements) with zero warnings. `curl_cffi`'s browser-TLS
impersonation (see `backend/app/services/yahoo.py`'s docstring) evidently
works from Render's IP range the same as it does locally. No proxy or
fallback data strategy was needed.

If this ever changes (Yahoo starts blocking Render's IP range later):
1. Check `backend/data_coverage_report.md` warnings and the `/api/health`
   response first -- a real block shows up as `Yahoo fetch failed: ...`
   warnings on every symbol, not an intermittent one-off.
2. Try redeploying to a different Render region (Oregon/Frankfurt/Virginia
   instead of Singapore) -- `region:` in `render.yaml`, then a manual
   deploy. A regional IP-range block is more likely than a global one.
3. If it's blocked everywhere on Render, the fallback is either (a) a
   paid rotating-residential proxy in front of `curl_cffi`'s session, or
   (b) accepting cached-only/staler data and leaning harder on the
   existing stale-quote-fallback mechanism (`app/routers/quote.py`)
   rather than trying to always fetch fresh.

## Environment variables

### Backend (Render dashboard -> nifty50-cfo-api -> Environment)

| Variable | Value | Notes |
|---|---|---|
| `CORS_ORIGINS` | `["https://nifty50-cfo-dashboard.vercel.app"]` | JSON array string (parsed by pydantic-settings). Must be updated any time the Vercel URL changes. |
| `ADMIN_REFRESH_SECRET` | (auto-generated by Render, `generateValue: true` in `render.yaml`) | Copy this value into the GitHub repo secret of the same name (Step 4). |
| `PORT` | set by Render automatically | The Dockerfile's `CMD` reads `$PORT` with an `8000` fallback for local/docker-compose use -- don't override this. |

### Frontend (Vercel dashboard -> nifty50-cfo-dashboard -> Settings -> Environment Variables)

| Variable | Value | Environment |
|---|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | `https://nifty50-cfo-api.onrender.com` | Production only |

Left **unset** for local dev (`frontend/.env.local` keeps it empty) --
`next.config.ts`'s `/api/*` rewrite to `BACKEND_INTERNAL_URL` (default
`http://127.0.0.1:8000`) still handles localhost. In production, an
absolute `NEXT_PUBLIC_API_BASE_URL` makes the browser call the Render
backend directly (cross-origin, hence the CORS_ORIGINS requirement
above) instead of going through that same-origin rewrite.

### GitHub Actions (repo Settings -> Secrets and variables -> Actions)

| Name | Kind | Value |
|---|---|---|
| `BACKEND_URL` | Repository **variable** | `https://nifty50-cfo-api.onrender.com` |
| `ADMIN_REFRESH_SECRET` | Repository **secret** | same value as the Render env var above |

## Redeploying

- **Backend**: Render is Blueprint-managed and connected to this GitHub
  repo -- push to `main` and it redeploys automatically. Manual redeploy:
  dashboard -> nifty50-cfo-api -> Manual Deploy.
- **Frontend**: not GitHub-connected on Vercel yet (the CLI's auto-link
  needs a GitHub login connection on the Vercel account first -- see
  `vercel git connect` or Vercel dashboard -> Settings -> Git). Until
  then, redeploy manually from `frontend/`:
  ```bash
  npx vercel --prod --token <VERCEL_TOKEN> --yes
  ```

## Scheduled refresh (Step 4)

`.github/workflows/scheduled-refresh.yml` runs daily at 06:00 IST (and on
manual "Run workflow"), POSTing to `/api/admin/refresh` with the shared
secret. That endpoint (`backend/app/routers/admin.py`) does two things:

1. Re-fetches NSE's constituent list -- **expect this to fail with a 403
   most of the time**, the same cloud-IP block `refresh_constituents.py`'s
   own docstring already documents; reported honestly in the response,
   not hidden.
2. Re-warms the quote/history/financials cache for all 50 symbols (this
   part reliably works, per the Step 1 finding above).
